# 限定WAN試験：承認待ちと実試験を分離する変更案

2026-10-26 JST。**レビュー用の手順改訂。未実装・未実行。** この文書の作成は、Wi-Fi変更、保持接続、サービス起動、転送保存への承認を意味しない。

**後続記録:** この案への本人承認後、[試験用helperの実装とオフライン検証](2026-10-26-WAN-PHASES-OFFLINE-VERIFICATION.md)まで完了した。以下は計画時点の記録で、ネットワーク設定変更・WAN試験は未実施。

最終ゴールは公開サイトで安全に操作・復旧できること。現在の段階は、携帯回線からhpへの到達を確認した後、一件BAN・明示解除を検証すること。今回の完了条件は、承認待ちが実試験の時間・照会枠・サービス寿命を消費しない手順、変更対象、復旧方法を具体化し、実装前に本人の確認へ出すこと。

## 1. 今回直す原因

[前回の記録](2026-10-26-PINNED-WAN-TRIAL-HOLD.md)では、二つの問題を確認した。

- `pin.py`の開始時から180秒・12照会を数え、承認待ちのkeep-aliveも実試験と同じ枠で消費した。
- `owner.py`も子process全体を180秒で制限し、`trial.py`は承認前に起動したHTTPSを利用した。したがってpinだけ直しても、親のtimeoutやHTTPSの240秒が先に尽きる。

旧証拠を変更せず、新しい試験用helperに限ってこれらの開始点を分ける。製品の性能改善、WAN到達の解決、NAT動作の保証ではない。

| 項目 | 改訂案 |

| BAN | 一件、TTL30秒。最新instance／revisionのpreviewから一度だけ適用・解除。256件上限・再起動で消える契約を維持 |

| HTTPS | 承認後の起動から240秒、Restart=no、停止猶予10秒を維持。Macの管理sourceと承認済み携帯sourceだけを許可 |
| 追加の承認待ち枠 | **Macの外向き保持接続だけ最大600秒・20照会。** 接続保持の照会間隔は40秒。WAN転送off、hpの試験サービス停止のまま |
| 開始準備枠 | 承認・ルーター認証・生きた同一接続が揃った時点から最大30秒。超過時は公開せず、保存結果不明なら復旧へ |

600秒・20照会・親900秒は今回新しく確認を求める運用上限で、測定結果や性能保証ではない。回線・照会先が保持接続を先に閉じれば中止する。待機中はMacから既存のHTTPS照会先への通常の外向き通信だけで、hpへのWAN接続やPiへのprobeを行わない。

待機枠は初期二宛先2照会と40秒間隔の保持照会を収容する。実試験枠12回は、承認後の最新source確認1回、予定するWAN接続5回それぞれのsource確認、開始準備と実試験中の保持照会を収容する。各段階で別々に計数・上限確認し、実装時に最悪スケジュールを検証する。復旧状態へ入ったら新しい照会・probeを追加せず、予備を失敗要求のやり直しに使わない。

## 3. 改訂する進行順序

### A. 準備：時計を始める前に終える

1. 試験用helperと検証をローカルで完成させ、製品・objectのhash、回復command、変更前状態を保存する。過去fixture・証拠は上書きしない。
2. 将来の新規対象は`/run/vhp-wan-20261026e/`と、`vhp-wan-20261026e-https.service`・`vhp-wan-20261026e-daemon.service`。既存path／unitなら保全して停止する。常設unit、account、enableは追加しない。
3. ルーターの試験転送`vhp-wan-20261025a`がoffであること、既存Pi／VPN転送と全体防御、現在のWAN IPv4を読む。認証は本人が行い、パスワードは受け取らない。
4. Macとhpの事前検査・新規一時配置を済ませる。hpのHTTPS・daemonは起動しない。Piは必要なbefore／afterの読取り確認に限り、設定・再起動・試験負荷を加えない。

### B. 承認待ち：Macだけの600秒枠

1. 必要なら承認済みWi-Fi一時DHCPを使い、有線en0の管理経路を維持する。元設定と所有する変更を記録する。
2. Wi-Fiの同じIPv4・TCP送信元portを二つの外部IPv4で使い、外向きsourceが一致した場合に一方のTLS接続を保持する。切断・source変化・Wi-Fi変化で終了し、自動再接続しない。
3. `run ID`、保持接続の識別、現在source、WAN側宛先、TCP18443、hp側宛先、製品hash、TTLとunit名を一組の確認票にする。本人へ実値と復旧方法を提示し、保存の承認を待つ。
4. ルーター認証が切れた場合もこの待機段階のまま、本人の再ログインを待つ。サービスや実試験の時計は開始しない。承認と認証の両方が揃う前に次へ進まない。
5. 600秒または20照会へ達したら、下書きを取り消し、接続終了とWi-Fi復元を確認する。後着の承認は終了したrunにしか属さず、新しいrunへ転用しない。自動で新しい承認要求を作らない。

ここで待機時間が長くても、次の段階には未使用の実試験12照会を渡す。承認直後に「待機枠の残り60秒」等を実試験の開始条件にしてはいけない。

### C. 承認成立から開始準備へ：一度だけ遷移する

1. 本人の回答と、その回答に対応する確認票を照合する。承認をhelperが自動生成せず、sourceやrun IDだけを書き換えて通さない。
2. 待機期限内で、承認・ルーター認証・同一の保持接続が揃った時点で、待機状態から開始準備へ一度だけ遷移する。開始準備には新しい30秒期限と実試験用12照会を与える。待機期限はここから先の時間判定に使わない。
3. 保持した同じ接続で最新sourceを照会し、承認値との一致、同じWi-Fi・TCP source、hp宛て有線管理経路を確認する。不一致なら中止し、新しいIPへ追従しない。
4. hpのNIC・既存XDP／TC・製品hash・port空き・既存サービスを再確認してから、source制限付きHTTPSを起動する。**ここがHTTPSの240秒の開始点。** LANの証明書・期待body、実cgroup filter、許可外source拒否を確認する。
5. 未保存の転送下書きが承認票と完全一致することを画面で確認する。事前検査を終えられなければ転送を保存せず復旧する。

### D. 実試験：保存直前から180秒

1. 保存の直前に、実試験180秒の監視と「転送offへの復旧義務」を記録・開始する。クリック成功後や再読込み完了後まで監視開始を遅らせない。保存結果不明も復旧対象にする。
2. 本人が承認した試験転送一件だけを保存し、再読込みで確定値と既存転送を確認する。保存失敗／不明を連打で解消しない。
3. 限定SYN観測を開始し、同じsource portからWANへ一度だけ接続する。通常の証明書検証、期待body、hpの実peerと承認sourceの一致を確認する。失敗ならここで終了し、XDPへ進まない。
4. 到達成功後だけdaemonを起動する。**ここがdaemonの180秒の開始点。** 空BANの正常通信と管理・LAN対照portを確認する。
5. 一件TTL30秒のpreview・BAN、実遮断とkernel counter差、LAN正常通信・管理の維持を確認する。新しいpreviewから未失効のうちに明示解除し、通信復帰を確認する。
6. daemon停止・所有XDP解除、解除後／detach後のHTTPSを確認する。予定するWAN接続はbaseline、空XDP、BAN中、解除後、detach後の5回。結果不明の変更要求は再送しない。
7. 実試験180秒へ達したら途中でも今回のサービスを停止し、転送offの復旧へ入る。期限到達時に新しい接続・BANを開始しない。

監視の時計は保存直前からなので、実際にonとなった時点より少し早い。180秒は新しい試験操作を止めて復旧へ移る期限であり、GUI操作不能でも180秒以内に転送offが完了する保証ではない。待機分を転嫁したり、未観測の公開開始時刻を後付けで置いたりしない。実試験中は人の追加承認や、準備コードの編集を挟まない。

## 4. 復旧方法と限界

承認待ちでの終了なら、未保存下書きのキャンセル、所有する保持socketのclose、Wi-Fi復元で終える。hpの試験サービスとWAN転送は開始していないことを確認する。

開始準備以降の失敗なら、既存の所有確認を使って今回のdaemonとHTTPSだけを停止し、XDP非装着・port待受なしを確認する。結果不明のBANは再送せず、停止後の状態と通信で判断する。Pi・既存サービス・未知XDPを停止／解除しない。

保存操作へ入った後は、結果が不明でも試験転送一件をoffへ保存して再読込み確認する。既存三転送と全体防御を照合する。GUI認証切れや管理経路障害でoffを確認できない場合は、**復旧未完了**として本人へ引き継ぐ。Macの監視processだけでF660Pを確実にoffにできるとは主張しない。hpのサービス上限は独立して働くが、転送offの代わりにはならない。

Wi-Fiは、現在状態が今回変更した状態であることを確認してから、記録済みの元方式へ戻す。既知の復旧commandは`networksetup -setmanualwithdhcprouter 'Wi-Fi' 192.168.1.9`。並行変更や所有不明なら上書きせず記録・引継ぎする。Ethernet、経路優先順位、Pi、router全体防御には触れない。

親processのfinallyだけを唯一の復旧保証にしない。SIGKILLや端末異常終了でfinallyが動かない場合に備え、所有する子processの終了確認、hpのサービス側上限、本人が使う対象unit停止と転送off・Wi-Fi復元の手順を残す。親900秒へ達しても復旧不能を成功扱いにせず、残存対象を報告する。

終了判定は、転送off、試験unit停止・非enabled、所有XDP非装着、試験process／待受なし、保持socket終了、Wi-Fi復元、有線管理・既存設定の保全まで。fixture・証拠は削除しない。

**Piの設定・サービスを変更しないことと、共用F660P保存時にもPiが絶対に瞬断しないことは別。後者は保証できない。** Pi側の不調や管理疎通の変化があれば中止する。完全な無瞬断が必須条件なら、ルーター変更を伴う段階は実施しない。

## 5. 承認後の最小実装対象と先行検証

製品には手を入れず、新しいprivate fixture内の`owner.py`・`pin.py`・`ipc.py`・`bind-source.py`・`trial.py`を変更する。

- `owner.py`：子全体180秒という制限を外側900秒へ置き換え、各段階の期限と復元結果を別々に記録する。
- `pin.py`：状態、各状態へ入った時刻、別照会予算を持つ。同一socketを引き継ぎ、待機期限・消費を実試験へ持ち込まない。証拠の終了とWAN成功を区別する。
- `ipc.py`：確認票のrunと承認対象を照合し、開始命令の再投入・後着命令を拒否する。ローカルprivate fileのままで、公開listenerを追加しない。
- `bind-source.py`：待機枠の残り70秒等で試験開始を判断する旧条件を、現在の状態・承認票・同一接続との照合へ置き換える。既存fileは上書きしない。
- `trial.py`：承認前に起動したHTTPSを読む前提を廃し、承認後の起動・検査・保存前監視・実試験・復旧を順に扱う。unitの240秒／180秒、接続timeout、BAN条件は維持する。

ネットワーク操作の前に、実時計・SSH・browserの代わりにfake clockと記録用アダプターで次を検証する。

| ケース | 必須の確認 |
| --- | --- |
| 承認待ち0／120／300／599秒、認証も有効 | 開始準備へ遷移した時点で実試験枠は12回・未使用。待機中にhpサービス起動・WAN接続・転送保存なし |
| 待機600秒ちょうど、後着承認 | 開始拒否。新しいrunへの転用なし。下書き取消し・接続終了・Wi-Fi復元へ |
| 承認後に開始準備を進め、元の待機期限を通過 | 旧待機期限を参照して中止しない。開始準備30秒と以後の実試験期限で判定 |
| 待機照会上限、source変化、保持接続切断、別runの承認、認証切れ | 未承認保存や自動再接続なし。認証切れは待機期限内で本人を待ち、期限切れなら終了 |
| HTTPS未起動／起動失敗／source制限失敗 | WAN保存・XDP起動なし。起動を試みた自分のサービスを監査・停止 |
| 保存応答消失 | 保存した可能性を保持し、今回の転送offが確認できるまで復旧完了にしない |
| 開始準備30秒・実試験180秒の境界 | 次の公開・BANを開始せず復旧。監視を途中で再起動・延長しない |
| WAN接続失敗、BAN結果不明、解除失敗 | 該当要求を再送しない。XDP／サービスの所有確認付き停止、転送off、通信確認へ |
| 各復旧処理の失敗、親timeout、強制終了相当 | 未完了を成功にしない。独立した上限・手動復旧対象を提示する |

この表は検証仕様であり、現時点の合格結果ではない。オフライン検証の成功も、実NAT／WANや本人による復旧の証明にしない。

## 6. 今回の確認事項

確認する変更は、**新しい試験helperへの上記改訂とオフライン検証、承認待ち専用600秒・20照会と親900秒の枠を採用すること**。この確認だけではルーター保存・WAN試験は開始しない。

実試験時は、最新source・WAN値・新規対象path・unit・製品hashと復旧方法を再提示して、具体的な保存承認を受ける。その後は今回合意した順序で処理し、人への追加質問で実試験の時計を消費しない。source不一致や復旧不能なら止め、条件を緩めて成功扱いにしない。
