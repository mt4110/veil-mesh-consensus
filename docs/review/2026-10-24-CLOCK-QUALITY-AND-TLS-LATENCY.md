# 時計品質による承認拒否とTLS更新後の適用待ち

2026-10-24。対象はLinux時計品質の運用条件、診断、通常daemonの受入試験。署名context、WAL形式、prepare/commit、定足数、時計の1秒誤差上限、RPC期限300ms、TLS更新後の3秒待ち、BANのTTLは変更しない。

## 時計条件の不整合

pi-nodeのsystemd 259.9はsystemd-timesyncdの既定の最大問い合わせ間隔2048秒を使用していた。アプリはadjtimexのTIME_OK・同期フラグとmaxerrorを検査し、maxerrorが1秒を超えたら新しい承認を拒否する。NTP同期表示yesとアプリの条件は同じではない。

読み取り専用のadjtimex観測では13秒間でmaxerrorが88,500usから95,000usへ6,500us増加した。500us/秒の増加では2048秒に1,024,000usとなり、1秒の上限を超える。これは時計の実際のずれを測った値ではなく、カーネルが報告する最大誤差の増加である。前回の拒否の瞬間には数値がログに残っておらず、その瞬間の値は未確認。ただし既定の問い合わせ間隔では周期的に承認できなくなる条件を再現できる。

[adjtimexの仕様](https://man7.org/linux/man-pages/man2/adjtimex.2.html)と[systemdの問い合わせ間隔設定](https://www.freedesktop.org/software/systemd/man/latest/timesyncd.conf.html)を参照。`deploy/systemd/timesyncd.conf.d/60-veil-clock.conf` は最大間隔だけを256秒に制限する。NTPサーバー、最小間隔、root distance、アプリの誤差上限は維持する。応答欠落が続けば引き続き拒否するため、任意のNTP障害下で可用性を保証する設定ではない。ホストへの配置と一度の再起動、問題時の保全付き復旧はユーザー承認済み。

## コードと診断

- 時計条件のエラーにstatus/flagsまたはmaxerror/budgetを残す。初回拒否と品質回復を記録し、同じ失敗が続く間は警告を繰り返さない。
- ローカル状態照会は現在の時計品質を再取得し、clock_quality、Unix/boot時刻、誤差を返す。古い承認時のエラーだけを表示しない。
- `veil_rpc_timing=debug` は既存wire bytesのSHA-256を診断IDとして送受信段階を対応付ける。診断無効時は計算しない。署名データの変更・再署名・追加タイムスタンプの送信はない。同一内容の再送は同じIDになる。
- 接続、送信、受信、永続化処理の各段階と、prepare/commitの種類・index・termを記録する。WAL段階は `veil_wal_timing=debug`、適用段階は `veil_apply_timing=debug`。所要時間は単調時計で測る。
- 承認拒否時の全ノード状態、要求のログ登録待ちと適用待ちの直近32サンプルを試験result.jsonに保存する。

ログには要求本文や秘密鍵を含めない。診断時刻は性能保証ではなく、ログ出力自身の影響も受ける。

## 定足数喪失試験の開始条件

時計設定前の再試験はTLS更新前のBANログ登録待ちで停止した。ログに、別の未確定高さがあるため提案できない旨が残った。失効はカーネル側で先に完了し、履歴を整理するRetireExpiredの合意はその後に進むため、失効確認直後のノード停止は整理エントリを未確定のまま残し得る。

既存の20秒の準備待ち内で、直前のBANの署名期限までの整理が全ノードで確定・適用され、未確定エントリがないことを要求するようにした。BANの5秒ログ登録待ち・3秒適用待ちなどは変更しない。状態照会のretired_through_unix_nsは確定ログと認証済みcheckpointからだけ計算し、未確定整理は含めない。既存の1高さ制約を維持する。

## ホスト設定適用後の確認

承認された新規drop-inを `/etc/systemd/timesyncd.conf.d/60-veil-clock.conf` に配置し、systemd-timesyncdを一度だけ再起動した。既存ファイルは変更していない。最大間隔256秒が反映され、NTP応答はIgnored=noでカーネルへ反映された。再同期後のmaxerrorは16.5ms、次の観測で43.5ms、最大間隔に到達した後の観測で91.5ms。statusはTIME_OK、未同期/時計故障/うるう秒移行フラグなし。NTPサーバー設定は従来のntp.ubuntu.comのまま。さらに256秒の最大間隔を経た4回目の応答もIgnored=noで受理され、その後の観測でmaxerror=31.5msへ戻ったことを確認した。

復旧が必要な場合は追加ファイルを `60-veil-clock.conf.disabled` に改名して保全し、サービスを再起動すれば元の最大間隔へ戻る。この復旧も承認済みだが、設定は正常に反映されたため実行していない。

## TLS更新後の3秒待ちの再現と段階ログ

設定後の通常daemon試験 `flow-after-clock-1` は全10段階を通過した。TLS更新後のBAN index=11について、最初の提案送信から全4ノードの最初の適用完了まで、同一ホストのログ時刻差で約0.557秒だった。後日のWAL再起動による再適用はこの集計に含めない。

次の `flow-after-clock-2` は、Linuxの2スレッド全体回帰と同時に開始した。全体回帰は163 passed / 0 failed / 6 ignored / 3 filtered。通常daemon側は目的のTLS更新後の3秒待ちで失敗し、期限直前からの全ノード状態と段階ログを保存できた。並行回帰自身は51.92秒で終了しており、TLS失敗瞬間まで同じ負荷が継続していたとは断定しない。

当該BANはindex=11、term=4。以下は同一pi-nodeのUTCログ時刻（所要時間のstageログ自体は単調時計で計測）。

| 段階 | 時刻・値 |
| --- | --- |
| 署名期限 | 03:04:55.466789 |
| 最初の提案送信 | 03:04:53.914830 |
| 最初のprepare証明送信 | 03:04:54.140659 |
| follower a/c/dのWAL file sync | 1.034 / 1.080 / 1.079秒 |
| leader bの適用完了 | 03:04:55.637336（期限後約171ms） |
| 最初のcommit証明送信 | 03:04:55.753802 |
| follower a/c/dの適用完了 | 期限後約379 / 394 / 404ms |
| 時計品質 | bounded、誤差37〜38.5ms、clock errorなし |

署名CLIのTTL=4秒は発行時刻を2秒戻すため署名直後の有効時間は約2秒であり、時計誤差分も保守的に差し引く。全台の合意・適用は最終的に進んだが、既に署名期限を過ぎていたためPassのままだった。全台Dropという判定は成立しない。この実行の失敗は、証明書の拒否や時計品質検査による停止ではなく、保存を含む進行の遅れによりBANの有効期間を消費したものと特定できた。期限切れBANを再発行・再活性化しない安全性は維持されている。

また、同じ区間のQUIC接続計測にも最大約797msがある。300msのtimeout設定は変更していないが、非同期タスクの再スケジュール遅延を含む実測時間は設定値を超え得る。これを797msの物理ネットワークRTTと解釈しない。Rustのfile-sync区間はFile::sync_all呼び出しの経過時間であり、SSD内部、カーネルのI/O待ち、スケジューラ、ログ出力、別プロセスの影響まで分離できたわけではない。

試験の待ち設定は3秒のままだが、同期的な状態照会の完了待ちを含むため、失敗を返した実経過は約3.596秒だった。最初の4ノード照会も約1.462秒掛かっている。この照会はローカルUnix socketであり、WAL処理が保持する状態ロックを待つ。今後の性能計測では制御状態の読取り待ちと合意時間を分ける必要がある。

両試験の終了処理でXDPなし・隔離試験パケット疎通成功を確認。独立確認でもvethにXDPなし、試験daemonの残存なし。最終macOS全体は162 passed / 0 failed / 1 ignored、clippy/fmt/diff検査通過。Linux側build/clippy、時計境界と復帰の回帰も通過した。

## 完了範囲と残件

時計の問い合わせ間隔と誤差上限の不整合は修正し、pi-nodeで反映・再同期・承認経路を確認した。TLS後の3秒失敗は同じエラー位置で再現し、段階ログから期限切れに至る経路を特定した。今回の時計修正・診断の範囲は完了。ただしTLS後のBAN適用待ちの間欠失敗そのもの、元の並行回帰安定化マイルストーン、小規模サイト導入全体は未完了である。

次の判断には、保存区間の長い停止を同じ実行のsyscall/ブロックI/O記録でさらに分解し、必要なdurabilityを保ったまま削減可能な保存があるかを確認する必要がある。今回の証拠だけでAya・NIC・SSD故障・第三者監視のいずれかを原因と断定しない。同期省略、TTL延長、タイムアウト延長、誤差上限引上げで合格させない。
