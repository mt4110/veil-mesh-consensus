## コードで確認した事実

### WALは追記ログではなく原子的置換スナップショット

`veil-node/src/infra/wal.rs:183` の `persist_observed` は毎回、新しい一時ファイルを `create_new` し、全スナップショットを `write_all`、`sync_all`、正本へ `rename`、親ディレクトリを `sync_all` する。成功した実保存1回につき同期呼出しは2回。起動時のロック・ディレクトリ作成の同期は別に数える。

`consensus_engine.rs:1893` はbincodeで状態全体を符号化し、`WalEnvelope { payload_bytes, sha256_checksum }` に格納する。二段階方式のpayload versionは9。投票、prepare/commit証明、選挙、進行証明、認証済みチェックポイント、初回適用期限等を保存する。

`consensus_engine.rs:1956` の復元はサイズ上限、末尾余剰バイト拒否、SHA-256一致、形式・context等を検査する。CRC付き可変長レコードを末尾まで走査する構造ではない。`wal.rs:49` は残存一時スナップショットがあれば保全・隔離を要求して再開を拒否する。

したがって、正本だけを事前確保しても次のrenameで別inodeに置き換わる。一時ファイルを毎回事前確保しても、その割当て・サイズ変更コストは毎回発生する。末尾へゼロを追加すれば現行デコーダが拒否する。固定長スロットやリングは保存方式の変更である。

SHA-256はここでは破損検出であり、任意に書き換えられるディスクに対する認証やロールバック防止を単独で提供しない。

### ロックの保持順序と影響

通常daemonの経路は以下の順序である。

```text
状態Mutexの非同期取得
  → ガードをspawn_blockingへ移動
    → 状態検証・変更・スナップショット生成
      → FileWal.writerの同期Mutex取得
        → create / write / file sync / rename / directory sync
      → writer解放
    → 遷移完了・状態ガード解放
  → 呼出し元再開 → 応答送信
```

根拠は `state_worker.rs:9`、`wal.rs:194`、`quic_mtls.rs:424`。`.lock`ファイルのOSロックはプロセス存続中の単一所有者保証であり、毎保存で取得し直すロックではない。4ノードで同一のアプリMutexを共有するわけでもない。

状態MutexはWAL処理中も保持される。そのノードのRPC状態処理、daemon tick、適用再試行、ローカル照会・緊急操作は同じ状態の順番待ちになる。既にカーネルへ設定されたXDPプログラムがこのRust Mutexを取得するわけではない。

これは「ロックを外せば直る」欠陥ではない。未永続の投票を次の遷移が追い越さないための境界であり、呼出し元のキャンセル後も維持する。`state_worker_tests.rs:61` 以降に、実行器の進行、保存前の応答禁止、キャンセル、保存失敗・panicの試験がある。今回はコード確認のみで再実行していない。

`quic_mtls.rs:239` 以降の `MeshNode` は `cfg(test)` 専用で、通常daemonとは異なる。テスト側の直接ロック＋同期処理を、通常daemonの実装と混同しない。ただし並行テスト負荷の評価では区別して記録する。

### バックデートは製品の署名CLIにある

`infra/approval_cli.rs:55` はSystemTimeから2秒引いた値を `issued_at_unix_ns` とし、BAN期限を `issued_at + ttl` に設定する。TTLが2秒以下なら署名を拒否する。`scripts/daemon-flow-check.py:244` はこのCLIを呼び、TLS更新後の試験は433行目でTTL=4秒、434行目で適用待ち3秒を指定する。

`usecase/authorization.rs:35` の承認条件は、観測時刻を `t`、誤差上限を `u` とすると `issued_at <= t-u` かつ `t+u < valid_until`。`domain/policy.rs:126` は満了が厳密に `issued_at + ttl` であることを要求する。適用は `ports.rs:61` で時刻の上界と時計速度の上限を使い、保守的なboot期限へ変換する。

署名CLI自身はここで検証済み時計品質を取得していない。pi-nodeの過去の正常な誤差値を、別端末の署名者や将来の全時刻の保証へ拡張できない。

## 一次資料との照合と、提案の修正点

### fsync、fdatasync、事前確保

[Linux man-pages](https://man7.org/linux/man-pages/man2/fsync.2.html)では、fdatasyncも読み戻しに必要なメタデータを同期する。ファイルサイズ更新は対象である。両者ともファイルだけの同期では名前の永続性を保証せず、ディレクトリ同期が必要になる。成功後の永続性はOS・デバイスが同期契約を守る前提であり、書込み中の全レコード原子性や将来の媒体故障まで保証しない。

[Rust 1.98.1の実装](https://raw.githubusercontent.com/rust-lang/rust/1.98.1/library/std/src/sys/fs/unix.rs)ではLinuxの `datasync` はfdatasync、`fsync` はfsyncに対応する。Appleでは両方ともF_FULLFSYNCである。この比較の性能判定をmacOS結果で代用しない。

[Linux v7.0のext4実装](https://raw.githubusercontent.com/torvalds/linux/v7.0/fs/ext4/fsync.c)は、journal経路で `datasync` に応じて `i_datasync_tid` と `i_sync_tid` を選ぶ。実装を「I_DIRTY_DATASYNCの有無だけで毎回全く同じ処理」と一般化しない。該当トランザクションが既に完了しているか、fast commit、barrier、他の書込みの状態にも依存する。これは上流v7.0の読解であり、pi-nodeのディストリビューションパッチと実マウント条件を照合したものではない。

現行の新規一時ファイル方式では割当て・サイズ変更・renameが残るため、大幅な改善を期待する根拠は弱い。ただし測定前に「必ず効果ゼロ」と断定する根拠もない。比較は採用判断のための小さな実験であり、解決を約束する変更ではない。

`set_len` は論理サイズ変更であり物理領域の予約とは異なる。[fallocate](https://man7.org/linux/man-pages/man2/fallocate.2.html)は領域を確保できるが、確保済み領域がすべて初期化済みで初回書込み時のメタデータ更新がないとは限らない。固定長ゼロ書込み＋初回同期も、以後のjournal経路やデバイス待ちが完全になくなる保証ではない。[ext4 journalの説明](https://docs.kernel.org/filesystems/ext4/journal.html)も、ファイルシステムのメタデータ整合性とアプリケーションデータの整合性を区別している。

将来セグメント方式にするなら、長さ上限・形式版・世代・LSN・親チェックポイントとの対応・チェックサム・永続化済み範囲を管理する。新しいチェックポイントとその参照が永続化する前に、必要な投票・証明を含む領域を再利用しない。CRC不一致やゼロ領域だけを根拠に正本を切り捨てて投票再開してはならない。送信済み投票を含まない未確定末尾だと証明できない場合は、保全して起動を拒否する。CRCもLSNも単独ではこの証明にならない。

### メモリ合意とクールダウン

現行 `two_phase.rs:286` は投票禁止表を更新してcheckpointした後に署名する。prepare証明もcommit投票の禁止表と一緒に保存する（433行目）。この順序を維持する。

提案方式への概念的反例：4メンバーA/B/C/D、Dが悪意を持ち、定足数3とする。A/B/Dの値Xへの証明をDが保留し、Aが未永続の投票履歴を失って再起動する。その後A/C/Dが競合値Yへ投票できれば、両証明の交差A/DのうちAが二重投票を防げず、Dは両方を提示できる。数秒待つだけではXの署名は消えない。これは変更案への反例説明であり、現行コードで安全性破綻を実行再現した主張ではない。

復帰には既存の永続履歴、または過去の署名が再利用できないことを証明する別の再参加プロトコルが必要。リーダー1台から確定状態を受け取るだけでは、未配送証明や未確定投票を知り尽くしたことにならない。

### 専用スレッド、Group Commit、同期回数

[Tokio 1.54.1のソース](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/task/blocking.rs)とローカルの同版ソースで、blocking poolの上限後のキュー待ち、開始済み処理をabortできないことを確認した。専用スレッドもOSのCPU割当て、I/O、起床待ちを受ける。

現在は状態Mutex取得後にworkerを作り、1ノードにつき同時に1遷移。さらに `two_phase.rs:324` は未確定高さを1つに制限する。そのままWALライターをチャネル化しても、呼出し元が保存完了を待つ間に同じ状態から次の保存要求を作れないため、Group Commitは自動的には成立しない。

`checkpoint()` の呼出し回数と実同期回数も異なる。`consensus_engine.rs:431` はスナップショットhashが前回と同じなら保存を省く。余分なprepare票による証明の作り直しを抑える処理も `two_phase.rs:401` に既にある。

一方、commit証明の保存（479行目）と、初回適用期限の保存（`prepare_leases`、`consensus_engine.rs:1595`）は異なる安全条件を守る。後者は部分適用・再起動時に期限を再設定しないために必要。「投票さえ保存すれば他は不要」とはしない。1件のBANの実保存回数は経路、再送、リーダー役、期限更新に依存するため、静的なcheckpointの個数から固定値を報告しない。

将来の集約方式には、未永続状態と永続状態の区別、永続化完了の通し番号、送信可能な応答との対応、失敗時の停止、上限付きキュー、キャンセル後の扱いが必要。prepareの送信がcommit成立の前提なので、単一BANのprepare/commitを無条件に同じフラッシュへまとめることもできない。異なるノードのWALを共有してまとめる方式は独立障害領域を崩すため提案しない。

### 時刻仕様

単にバックデートを削除すると、時計品質が正常でも `issued_at <= t-u` を満たすまで承認が拒否され得る。`now >= issued_at-max_skew` は、その保守的な開始条件を変更する。意図した仕様変更として評価すべきであり、I/O改善には数えない。

最小の別案は実際の署名時刻を発行時刻にして絶対満了を固定し、受理可能になるまで待機または再試行する設計。ただし待機・配送・合意時間を含むため、適用後に丸ごとTTL秒の遮断は保証しない。即時受理のためにnot-beforeと発行時刻を分ける案は、署名対象・検証意味・構成互換性も設計する。各ノードの合意成立時刻から期限を再計算する案は採用せず、遅延catch-upでも同じ署名期限を使用する。

## 6時刻ラッパーの修正採用

提供コードをそのまま置き換えに使わない。現行のスナップショット置換を追記に変えてしまい、状態ロック待ち、rename、ディレクトリ同期を測れないためである。時刻だけ記録して後から出力する方針は採用する。

| 計測境界 | 得られる経過時間 | 得られない結論 |
| --- | --- | --- |
| 状態ロック要求→取得 | 同じ状態の待ち行列 | どの先行処理が原因かは操作IDとの対応が必要 |
| spawn直前→closure開始 | blocking pool投入後の待ち | pool上限、スレッド作成、OS run queueを単独では区別できない |
| WAL writer lock前→取得 | writer取得待ち | 今の直列経路では通常小さいはずだが未測定 |
| serialize/create/writeそれぞれ前後 | 個別処理の経過時間 | write_allは複数write syscallになり得る。必ず1回という意味ではない |
| file sync直前→直後 | 同期呼出しの経過時間 | SSD内部、journal、I/O待ち、実行再開待ちを分離できない |
| rename、directory sync各前後 | 置換・名前の永続化の経過時間 | ファイル同期だけの短縮が全体改善かを別途評価する |
| closure末尾→await復帰 | 結果配送・drop・スケジューリング等 | 特定のTLS処理やログが犯人とは断定できない |

closure終了時刻はfile sync直後ではなく、残りの状態処理やガード解放を区別できる位置に置く。合計と内訳の対応を確認する。区間には同一プロセスのInstantを用い、Unix時刻は署名期限・他プロセスとの対応に使う。Instantをプロセス間で直接引かない。

固定上限の記録領域へ時刻・操作ID・ノード・view/index・段階・バイト数・結果を残す。本文や秘密鍵は記録しない。現行 `persist_observed` は境界コールバック内で同期ログを出すため、ログ出力時間が次の区間へ混入し得る。次の計測版ではそのログをクリティカル区間から移す。

成功時にtupleを返すだけでは、呼出し元キャンセルで証拠を失う。保存失敗、panic、キャンセルも記録し、集約出力は状態ロック解放後、可能ならRPC応答送信を遅らせない経路で行う。記録キューに上限と欠落数を持たせる。閾値50msのログだけでは分布を算出できないため、軽量な全件カウンタと遅い処理の詳細を分ける。

6時刻計測で得られるのは遅延区間であり、「1回で真犯人100%確定」ではない。QUIC transport統計とアプリ応答時間の比較は有効だが、transport遅延にはネットワーク・相手側も関与し、RPC遅延にはロック以外の検証・保存も関与する。

## 次の最小変更案と検証条件

実装着手は別の依頼で行う。推奨順序は以下。

1. 保存手順を変えず、上記の区間計測と実保存回数を記録する。既存ログの計測への混入を分離する。
2. Linuxの一時スナップショットのfile syncだけをfdatasyncにした比較版を作る。正本置換・directory sync・0600・単一所有者・サイズ上限・復元形式はそのまま。失敗を握り潰したり同期なしへfallbackしない。
3. 効果がなければ採用せず、支配的区間と必要保存回数に基づいて、重複保存またはround待ちの局所改善を一つ選ぶ。固定長化・Group Commitはそこで必要性を判断する。
4. バックデートの仕様は独立して評価・変更する。性能比較の前後に混ぜない。

固定する条件：同じ4プロセス・同じSSD、WAL内容/サイズの初期条件、同じビルド条件、TTL=4秒、バックデート2秒、TLS後待ち3秒、RPC connect/response各300ms、時計上限1秒、定足数、承認・membership・prepare/commitの検証。NTP品質は固定値と仮定せず毎回記録する。ログ設定も揃える。

比較順序はA/Bを交互にし、単独実行と並行回帰を別集計する。並行負荷はプロセスの実稼働時間も記録し、TLS段階と重なったかを確認する。署名完了→受付→prepare→commit→各ノード適用→実パケットDropを分け、署名期限までの余裕を記録する。CLI照会による遅延と実際の適用時刻を混同しない。

初回の比較枠案は単独・並行それぞれA/B各10回を上限とする。これは探索枠であり信頼性認定ではない。全試行の失敗も残し、中央値・最大・試行数・期限内適用率を示す。少数標本からp99を保証しない。どちらも再現しない場合は「修正済み」でなく「効果判定不能」とする。元の3秒waitは同期照会により実経過が超過し得るため、設定値と実測を併記する。

安全性の確認条件：write/file sync/rename/directory sync各段階のエラー・停止、同期前の署名送出禁止、キャンセル後の排他、再起動後の同一view/height競合票拒否、prepare/commit証明とチェックポイントの復元、期限切れBAN不復活、部分適用の期限不延長、WAL欠損・破損・余剰バイトの拒否。親ディレクトリ同期に失敗した場合も投票を続けない。

プロセスkill試験はホスト電源断の保証ではない。電源断相当の検証は破棄可能なVM/専用媒体など別環境と明示的な実施範囲が必要。比較試験の成功だけで任意のストレージへの耐障害性や独立4ノード構成の成立を主張しない。

## 今回どこまで進んだか

進んだのは設計判断と検証計画である。保存形式、状態ロック境界、バックデートの所在を確定し、チェックリストの該当と非該当を分けた。危険な復帰・同期省略案を除外し、最小の比較対象を定義した。

進んでいないのは実測性能と障害解消である。新しい計測コード、fdatasync版、実機再試験は未実施。約1秒の原因の内訳も未確定であり、TLS後タイムアウトは未解決のまま扱う。
