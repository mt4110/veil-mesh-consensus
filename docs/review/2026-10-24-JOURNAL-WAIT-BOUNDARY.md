# 必須fsyncのジャーナル待ち：調査範囲と設計上の分岐

最終ゴールは安全に使える無償OSS、現在のマイルストーンは小規模サイト試験導入。今回は前回のフェーズ即時送信修正を基準とし、WAL保存方式、file/parent sync_all、TTL、試験期限、保存前の署名送出禁止を固定する。証拠は `artifacts/journal-wait-f8_fj5_a/`。

## 確認条件

対象はpi-nodeのLinux 7.0.0-38-generic、x86_64、SATA SSDのsda5/ext4。`/proc/fs/ext4/sda5/options` で `data=ordered`、`barrier`、`commit=5`、`min_batch_time=0`、`max_batch_time=15000` を確認。ファイルシステムの累積errors_countは0。ただしこの値はSSD健全性を保証しない。

[ext4公式資料](https://docs.kernel.org/admin-guide/ext4.html)が説明するmax_batch_timeは、同期書込みをまとめるための意図的な待ちの上限15msであり、同期全体の上限ではない。`commit=5` を「fsyncは5秒待つ設定」と読むのも誤り。15ms設定だけを約1秒の停止の原因とする根拠はない。

実行バイナリは前回の `tests-phase-final`、SHA-256 `94c98c76ecd875bd32a27da179a549439d7aaf4f7a1771fc0e50f6c57668918f`。前回の11ソースのhashと一致し、今回の開始時点のveil-node/src配下51ファイルも保持した。製品ソース・試験条件・依存の変更は行っていない。

## 今回増やした観測

前回のtraceにはfd番号しかなく、長いfsyncが一時WALか親directoryかを判別できなかった。今回は `strace -f -y -ttt -T -e trace=fsync,fdatasync` で自身が起動した試験の同期対象パスを識別する。ファイル内容・鍵・ネットワーク本文は収集しない。

100ms間隔でsdaのdevice全体のstat、集計PSI、試験threadのstate/wchan、対象journal threadのstatをメモリに記録し、試験終了後に出力する。同期ログは通常の同一ファイルシステム上であり、ptrace・追加ログによる観測負荷は残る。traceあり実行とtraceなしの回帰は分ける。

[Linux I/O統計の仕様](https://docs.kernel.org/admin-guide/iostats.html)に従って、flush完了数・flush累積msをdevice全体で読む。これらは当該WALだけの値ではなく、他の書込みも含む。前後100msの区間に含まれる累積msを、単一のfsyncや単一SSDコマンドの所要時間と同一視しない。

tracefsはrootのみアクセス可能、perf_event_paranoid=4、journal threadのwchanも0であり、一般権限でjournal内部の各段階やblock requestとの対応までは取得できない。0を「待っていない」と解釈しない。権限やホスト設定を変更して観測範囲を拡張していない。

正確な試験時間はtest.log、observerの全体経過時間はmeta.jsonで区別する。新たに書いた観測・集計スクリプトは証拠ディレクトリに保持し、保存データは後から再集計可能。同期対象はパスと終了後のfile typeで分類し、消失したパスは不明として扱う。

取り直しの589.238msは `veil-fix-...-85` ディレクトリのfsyncで、同じTID=1876231のサンプル6点がD/jbd2_log_wait_commit。開始UNIX時刻1792821273.017347。同区間内の1792821273.380967〜.481569のデバイス統計差分で、flush完了数+1、flush累積時間+436msを観測した。100msで436ms処理した意味ではなく、以前から進行していた処理の完了がその区間に計上される。これにより、ブロック層で計測される長いflushがjournal待ちと同時に発生することまで確認した。全回帰には起動・復旧の保存も含まれ、最大値を特定のBANのPrepare保存と誤って対応付けない。

この統計はデバイス全体であり、個別のflushを当該fsyncに対応付けるtracepointは未取得。デバイスの内部動作、ドライバ／キュー待ち、他の書込みのどれが何msかは確定できない。SSD故障・特定プロセス・セキュリティ監視を原因とする根拠もない。

### 実行管理上のミスと除外した比較

最初のparallel-1が終了する前にtraced-parallel-1を開始してしまい、2組の回帰が重なった。この2実行は通常並行回帰の採否から除外し、記録を残して両者終了後にparallel-2→traced-parallel-2を直列に取り直した。重複実行も各175成功だったが、通常条件の再現性の証拠には使わない。

重複中は一時WAL最大1,255.499ms、directory最大997.168ms。同じTIDのjournal待ち、デバイスflush累積時間の増加も観測した。ただし通常条件との差を定量的な負荷効果・改善率として扱わない。`experiment-notes.json` に重複した実行名を明記した。

## 今回の判定

**切り分けは進んだが、安全な短縮は未達。製品コードは変更せず、現方式の採用条件を緩めない。** 今回の非重複の単独・並行回帰は成功した。しかしコードも環境も改善していないので、前回の失敗解消・安定性向上・期限内保証とは扱わない。macOSのfmt/diffも確認。Linuxの実XDP、TLS更新3秒、B3のリーダー停止試験は今回再実行していない。

次の分岐は、(a)現方式を独立した物理ストレージで比較する、または(b)以下の保存コンテナの小さな試作で同期回数削減の効果を見る、である。どちらも短縮を保証しない。現ホストのままさらに原因を追うなら、対象sda5のjournal transactionとblock flushの発行／完了を対応付ける権限付きtraceが必要になるが、今回はホスト権限・設定を拡張していない。

## 現方式のまま採用しない変更

- directory syncの省略・同期順序の変更：renameの永続性が失われる。[fsyncの仕様](https://man7.org/linux/man-pages/man2/fsync.2.html)でもdirectoryの明示同期は別に必要。
- cache/barrier無効化、tmpfsへのWAL移動、非同期応答：今回の永続化条件を満たさない。
- 保存前のロック解放、thread追加、QUIC変更：必須fsync内部のjournal待ちを短縮する証拠がない。保存未完了状態を後続の投票に見せる変更は行わない。
- 毎回のset_len/fallocate：毎回新規一時ファイルを作る方式では割当て・rename・directory同期は残る。既存の正本だけ事前確保しても次のrenameでinodeが変わる。
- max_batch_timeの変更：今回の15ms上限と約1秒停止の差を説明できず、ホスト全体の設定変更を混ぜない。

現在の1回の状態保存にはfile fsyncとdirectory fsyncの2呼出しがある。不要な重複保存の削減とは別問題であり、必須2呼出しを現方式のまま1呼出しへ単純に減らす安全な修正は採用しない。

## 現方式で不足する場合の最小設計案（未実装）

まずコードを変えずに評価できる分岐は、別の物理デバイス／独立したホストへのWAL配置である。同じSSD内の別ディレクトリは、journalやdevice flushの共有をなくさない。移動だけで期限内完了を保証できず、別媒体の比較結果も今回はない。

保存形式を変える場合の最小候補は、投票差分ログやリングではなく、**現行の完全スナップショットをフレーム化して追記し、定期的に現行の原子的置換で圧縮する方式**。合意payloadと復元検証を再利用し、FileWalの外側のコンテナを変更する。

1. フレームに形式版、長さ上限、世代・連番、前フレームとの連鎖hash、既存snapshot bytesと全フレームchecksumを持つ。node/cluster/config bindingは復元時に既存payloadも検証する。チェックサムは媒体を任意改変できる攻撃者への認証ではない。
2. 通常保存は完全フレーム追記→file.sync_all成功→その保存を待っていた遷移の応答解放。file syncは省略せず、完了前の票は返さない。初期ファイル作成時はfile syncとdirectory syncを完了してから使用する。
3. 作成・renameがない定常追記ではdirectory syncを毎回行わずに済む可能性がある。ただしi_size/割当て更新とjournal/device flushは残る。**fsync回数の削減候補であり、単一fsyncの1秒停止を解消する保証はない。**
4. byte上限・frame数上限で圧縮。現在の容量上限を無断で拡大せず、次フレームの追記が上限を超える前に圧縮する。header分を含め1フレームも収まらなければ停止する。最新完全snapshotを新世代の一時ファイルへ書き、file sync→rename→directory syncを完了してから次の追記を開始する。圧縮の同期は投票解放の前に完了させる。総容量と一時ファイル分の予算、ENOSPC時の停止を規定する。
5. 復旧は世代・連番・連鎖・checksum・長さと既存の安全条件を検証。**不完全／不正な末尾を見つけたときは起動拒否・保全する。** CRC不一致を「未ackの末尾」と推測して自動切捨てしない。既にackした投票の破損との区別ができないためである。構造が完全な未ackフレームを採用する場合も、投票やロックを保守的に維持することを検証する。
6. 旧WALは停止中に明示移行し、元の証拠を残す。未知形式・移行途中・不確定renameから古い状態へ自動fallbackしない。

採否の検証条件は、書込み途中、file sync前後、圧縮rename前後、directory sync失敗、キャンセル、再起動後の競合投票、遅延QC、期限切れBAN、容量上限、形式移行。現在の同一期限で単独・並行比較を行う。プロセス停止だけでは電源断耐性を証明しないため、保存形式変更の採用前には破棄可能な専用環境でのクラッシュ検証が必要。

変更箇所はFileWalの保存・読出しコンテナ、main.rsの起動時容量検査とload_walへの受渡し、初期構築・移行経路とその試験に限定する案である。既存のload_walは単一snapshotを読むため、保存側だけを置き換えて済むとはしない。

この案は今回の固定条件を超えるため実装していない。まず上記の構造差に効果があるかを独立した試作で測り、効果がなければ合意コードを巻き込んだ大改修へ進めない。
